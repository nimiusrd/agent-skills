# Stacked PR の作成と更新

stacked PR は、最下段を main などの統合先ブランチに向け、各子 PR を直下の親 PR の head ブランチに向ける。各 PR のレビュー対象は親からの差分であり、stack 全体の差分ではない。

## 構成を確定する

- 各段の目的、head のリポジトリ・所有者・ブランチ、base、親 PR の URL と状態を確認する。既存ツールの stack 情報、GitHub 上の PR、コミットの祖先関係を照合し、ブランチ名や分岐元だけで依存先を決めない。
- 既存 PR の修正と新しい段の追加を区別する。追加する変更を親の公開ブランチに混ぜない。未公開の変更を分割する場合は、全体の差分を保ったまま、親から順に各段が成立するようブランチとコミットを組み立てる。
- 親までの変更を含めて各段が動作し、その段に必要な検証を実行できる分割にする。子の変更がないと成立しない親を作らない。分割前後の最上段の内容を比較し、変更の欠落・重複・意図しない追加がないことを確認する。
- 親が未マージのまま closed なら、親を自動的に飛ばしたり再公開したりしない。依存が解消できるか調べ、依頼の範囲で決められない場合だけ確認する。merged の親は後述の追従手順で扱う。

## ツールの選択

リポジトリで使っている stack 管理ツールがあればそれを尊重する。GitHub 公式の stacked PR 機能を使う場合は、対象リポジトリでの利用可否と `gh-stack` 拡張の有無を確認し、導入済みの版のヘルプに従う。公式機能は public preview で、全ブランチが同じリポジトリにある必要がある。[公式の概要](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs)

管理ツールが使えない場合も、Git と `gh pr create --base <親ブランチ> --head <子ブランチ>` で依存する PR を作成できる。base を連ねただけの PR と、GitHub 公式機能に登録された stack は区別する。前者では親のマージ後の rebase や base の付け替えを自分で管理し、公式機能の自動処理を前提にしない。fork を含む場合は、その公開先で親ブランチを base に指定できるか確認し、未対応の構成を作らない。[PR 作成コマンド](https://cli.github.com/manual/gh_pr_create)

## 作成・公開

1. 各 head の既存 PR を base で絞らず調べる。本体の再実行ルールに従い、一致する open PR を更新し、重複作成を避ける。
2. 最下段から順に、各段のステージ済み差分・コミット・親からの差分を確認し、検証して公開する。親の修正が子のレビュー差分に混ざっている場合は、追従を済ませてから本文を作る。
3. 各 PR のタイトル・本文はその段の base から head までの変更を表す。リポジトリのテンプレートを守り、背景・レビュー観点などの対応する項目に親 PR のリンク、その段の役割、レビュー順を記載する。検証結果は実際に検証した段に対応させる。
4. 管理ツールで一括公開する場合も、公開する全ブランチと PR が今回の対象であることを確認する。結果を再照会し、各 PR の head・base・状態・本文と stack の順序を確認してから完了を報告する。特に手動管理では、base が作業ブランチになる子 PR でも必要な CI が起動するか確認し、未実行や pending を成功と扱わない。

`gh stack` を使う際の確認点:

- `submit` は複数ブランチの push と PR 作成を伴う。自動生成されたタイトル・本文に依存せず、各段の最終差分から本体の書式に整える。`--auto` は新規 PR を draft にし、`--open` は既存 PR も ready にするため、既存の draft 状態を一括で変えない。
- `link` は既存 PR の base も変更し得る。予定する親子関係と既存 base が一致するか先に確認し、意図しない付け替えを避ける。
- `push` は各ブランチに `--force-with-lease` を使い、更新は一括で成功・失敗するとは限らない。`sync` も rebase と push を伴い得る。本体の force push 制約と変更追従の例外は、これらのラッパーコマンドにも適用する。

コマンドの引数・副作用は [GitHub 公式 CLI リファレンス](https://docs.github.com/en/pull-requests/reference/stacked-prs-cli-commands) で確認する。

## 親の更新・マージへの追従

1. 更新前に各段のローカル・リモートの head と親子の境界コミットを記録し、今回追従する子孫を特定する。作業ツリーの未コミット変更を保護し、未取り込みの他者の変更があれば先に状況を確認する。
2. 親に修正が入ったら、必要な子孫を親から順に新しい親へ載せ直す。統合先ブランチの更新への追従では、必要に応じて最下段から載せ直す。この変更追従に必要な rebase と `--force-with-lease` による再公開は、本体の例外に従いユーザーへの確認なしで進める。
3. 親がマージ済みなら、まず GitHub 上の base と head を再取得する。公式機能による自動 rebase・付け替えが済んでいれば、その結果にローカルを追従させる。手動管理で squash/rebase merge によりコミット ID が変わった場合は、保存した旧親の境界を使う `git rebase --onto <新base> <旧親の境界> <子>` などで子固有のコミットだけを移す。base の変更だけで親の差分が消えると決めつけない。
4. 追従後は各段の差分と必要な検証を確認してから push する。履歴を書き換える場合は、確認したリモート head を期待値とするブランチごとの `--force-with-lease=<ref>:<期待するhead>` を使い、他者の更新を上書きしない。lease が拒否されたらリモートを再照会して差分を確認し、期待値だけを更新して再試行しない。
5. PR の base と本文を現在の親子関係に合わせる。依頼された追従に必要な base 変更は範囲内で行うが、異なる依存先への再構成や無関係な PR の付け替えまで広げない。競合や権限などで止まった場合は、公開できた段、未反映の段、復旧に必要な情報を報告する。途中失敗後は状態を再照会して未完了分だけを再開する。

管理ツールによる追従の詳細は [stack の管理](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/managing-stacked-pull-requests) を参照する。PR の作成・更新だけを依頼された場合、stack のマージは実行しない。
